# Folio Functionality Audit

**Architecture:** one processing path. The browser is a client (React/Vite + PDF.js previews); every
document operation runs on Folio's server through the authenticated job API. There is no
local/cloud mode selector.

**Tool registry:** 36 tools in `src/lib/engines.ts`, all with `side: 'server'`, plus one additional
server handler (`pdf-to-csv`) → **37 job API handlers** in `server/pipeline.mjs`.

**Engines deployed:** qpdf · poppler-utils (`pdftoppm`, `pdftotext`, `pdfinfo`) · Tesseract ·
LibreOffice (`soffice`) · ImageMagick · pdf-lib + first-party OOXML/XLSX writers.

## Verification method

- Real files are generated by `tests/server.test.mjs` fixtures (multi-page PDFs, a DOCX, images) and
  pushed through the public job API: create → upload → start → poll → download.
- Every PDF output is reopened with `pdf-lib` and its page count, page order and page boxes are
  asserted; JPEG outputs are checked by signature; the Word→PDF output is re-extracted through
  `pdf-to-text` to prove no `<w:…>` markup reaches the document.
- Authorisation is asserted: cross-origin POST → 403, another session's job → 404.

## Known architectural limitations

- Everything runs on the server, so a job requires an upload; the UI states this before processing.
- The runtime is 1 vCPU / 1 GB: heavy engines are serialised, so concurrent large Office or OCR jobs
  queue instead of running in parallel.
- PDF → Office conversions are structural reconstructions, not byte-faithful Word round-trips.
- No engine produces a cryptographically signed (certificate) PDF; signatures are visual overlays.
- veraPDF and pyHanko are not installed, so PDF/A validation and certificate signing are not offered.
